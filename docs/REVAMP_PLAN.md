# Revamp Plan — Path to a Market-Competitive Release

This is a prioritized engineering plan for taking Stock Analyzer from a
well-engineered hobby/portfolio project to something that stands up to scrutiny
from a quant, a hiring manager, or a discerning user. It is ordered by
impact-per-effort. Effort estimates assume one experienced developer and are
expressed in focused working days (d).

The single most important theme: **the headline 79.7% accuracy is in-sample
training accuracy.** `ml.trend.train` fits on the full dataset and then scores
`predict(X)` on that *same* `X`. For a trend model this number is close to
meaningless as a measure of predictive power. Everything in Tier 1 exists to
replace that number with an honest, out-of-sample one — and to make the claim
defensible rather than impressive-sounding.

---

## Tier 1 — Credibility (do these before promoting the project)

### 1.1 Walk-forward / out-of-sample evaluation vs naive baselines — **3–4 d**

**Problem.** The reported accuracy is computed on training data; there is no
temporal hold-out, so it tells us nothing about forward performance and is
almost certainly inflated by overfitting.

**Plan.**
- Add `ml/evaluate.py` with a time-ordered walk-forward harness: expanding (or
  rolling) window, train on `[t0, t)`, evaluate on `[t, t+h)`, advance, never
  letting future bars leak into a training fold. The existing
  `_stratified_k_fold` shuffles across time and must **not** be reused for the
  reported headline number — keep it only for hyperparameter selection within a
  training window.
- Report out-of-sample accuracy, macro-F1, and a confusion matrix aggregated
  across folds.
- Compare against three naive baselines that any honest writeup must beat:
  1. **Majority class** (predict `sideways` always).
  2. **Persistence** (predict that the next 10-day bucket equals the last one).
  3. **Stratified random** (sample from the class prior).
- A model that does not beat all three out-of-sample is not worth shipping a
  number for — say so plainly in the README.

**Done when:** README's "Training Results" table is replaced by an
out-of-sample table with baseline columns, regenerated by a single command.

### 1.2 Committed, reproducible `metrics.json` — **1–2 d**

**Problem.** Metrics depend on live `yfinance` data, so they drift daily and
cannot be regenerated to match a committed claim. There is no committed metrics
artifact at all today.

**Plan.**
- Freeze a dated OHLCV snapshot (parquet) under `ml/data/` for the default
  universe; add a `--from-snapshot PATH` path to `prepare_training_data` so a
  run is bit-reproducible.
- Commit `ml/models/metrics.json` generated from that frozen snapshot, with the
  snapshot date and git SHA embedded.
- Add a CI job (or a `make verify-metrics`) that retrains from the snapshot and
  asserts the committed `metrics.json` still matches within tolerance — turning
  the published numbers into a tested contract.

**Done when:** `metrics.json` is in the repo, regenerates deterministically, and
CI fails if a code change silently moves the numbers.

### 1.3 Honest accuracy framing in the README — **0.5 d**

Reword the "Training Results" section to label numbers as in-sample vs
out-of-sample, show the baseline deltas, and keep the existing "not financial
advice" disclaimer prominent. This is cheap and is the difference between a
project that looks competent and one that looks oversold. Depends on 1.1/1.2.

## Tier 2 — Demonstrability (makes the work legible to others)

### 2.1 Screenshots and a short demo video — **1–2 d**

**Problem.** This is a desktop app whose value is visual; the README has no
imagery. A reviewer cannot see the simulator, charts, or ML signals without
building it.

**Plan.**
- Capture 4–6 annotated screenshots: snapshot view with ML trend + confidence,
  anomaly flags on a chart, the trading simulator with live P&L, sentiment
  panel. Store under `docs/assets/`.
- Record a 60–90s screen capture (analyze a ticker → read the ML signal → run a
  simulated trade) and link it at the top of the README.
- Embed the screenshots in the README feature section.

**Done when:** A first-time visitor understands what the app does in under a
minute without cloning it.

### 2.2 The from-scratch-GBDT blog writeup — **2–3 d**

**Problem.** The from-scratch NumPy gradient booster (`ml/gradient_boosting.py`,
~600 lines) is the genuine technical crown jewel, but its depth is invisible in
a feature list.

**Plan.** Write a standalone technical post (publish on a blog and cross-link
from the README) covering:
- The XGBoost-style second-order objective: leaf values as Newton steps
  `w* = -G / (H + λ)`, the gain formula, and why hessians beat plain gradient
  descent here.
- Softmax cross-entropy with one tree per class per round.
- The exact-split vs histogram trade-off, with the committed benchmark numbers
  (custom vs sklearn `HistGradientBoosting`) showing accuracy parity and the
  ~13× training-time cost — and *why* that trade was chosen.
- A correctness argument: matching sklearn within ~1% is the evidence the math
  is right.
Reuse the synthetic benchmark in `benchmarks/bench_gradient_boosting.py` for the
figures so the post is reproducible.

**Done when:** There is a linkable artifact that demonstrates the model was
built and understood from first principles, not wired together from a library.

## Tier 3 — Product depth (turns a demo into something usable)

### 3.1 Model confidence calibration — **2 d**
The classifier reports a confidence (max softmax probability) that is almost
certainly uncalibrated. Add reliability diagrams and temperature scaling /
isotonic calibration on a hold-out fold so "78% confident" actually means
roughly 78% hit rate. Calibration error (ECE) belongs in `metrics.json`.

### 3.2 Backtest the signal, not just the classifier — **3–4 d**
Accuracy on a 5-class bucket is not P&L. Wire the trend signal into the existing
trading simulator as a strategy and report risk-adjusted returns (Sharpe, max
drawdown, hit rate, profit factor) vs buy-and-hold on the same out-of-sample
window. This is the number a user actually cares about.

### 3.3 Feature and data hardening — **2 d**
- Handle the missing-class case in `TrendClassifier.predict` explicitly: the
  estimator only emits probabilities for classes seen in training, so the
  returned `probabilities` dict can have fewer than five keys (covered by the
  new round-trip test). Decide whether to back-fill absent classes with 0.0 for
  a stable API contract.
- Add survivorship-bias awareness to the data note (the 25-ticker universe is
  today's large caps, not the universe as it was 2 years ago).

### 3.4 Broaden and document the universe — **1–2 d**
Make the training universe configurable from a committed manifest rather than a
hard-coded list in `ml.trend.train`, and document the selection rationale.

## Tier 4 — Operational polish

### 4.1 Pin transitive security upgrades behind a framework bump — **1 d**
`fastapi==0.115.12` pins `starlette<0.47.0`, which keeps the project on a
starlette version with known advisories (CVE-2025-54121, CVE-2025-62727,
PYSEC-2026-161). The fix requires a FastAPI minor bump (a deliberately-deferred
0.x change). Schedule it as an isolated upgrade with a full test + manual smoke
pass, since 0.x minors can break.

### 4.2 Coverage reporting + ratchet — **1 d**
Add `pytest --cov` with a coverage floor in CI so the 45-test suite cannot
silently regress as the surface grows.

### 4.3 Frontend dev-tooling vulnerability — **0.5 d**
The remaining `npm audit` findings are the esbuild/vite dev-server advisory
(GHSA-67mh-4wv8-2f99), fixable only via `vite@8` (a major bump). It affects the
dev server, not the shipped Electron bundle. Schedule the Vite 8 migration
deliberately rather than as a drive-by `--force`.

---

## Suggested sequence

1. **Tier 1 in full** (≈5–7 d) — this is the credibility gate; nothing else
   matters if the headline number is in-sample.
2. **2.1 screenshots/video** (≈1–2 d) — cheap, high marketing leverage.
3. **2.2 blog writeup** (≈2–3 d) — showcases the real differentiator.
4. **Tier 3** as product investment warrants.
5. **Tier 4** folded in opportunistically.

Total to a credible, demonstrable v1: roughly **8–12 focused days**, front-loaded
on honest evaluation.
